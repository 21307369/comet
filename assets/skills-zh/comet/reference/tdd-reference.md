# TDD 参考

规范路径：`comet/reference/tdd-reference.md`

本参考文档补充 Superpowers `test-driven-development` 技能，融入 mattpocock/tdd 的增强实践。在 build 阶段编写测试时参考本文档。

## 好测试的标准

测试通过公共接口验证行为，而非实现细节。好测试读起来像规格说明，能经受重构，因为它不关心内部结构。

**好测试的特征：**
- 测试用户/调用者关心的行为
- 只使用公共 API
- 描述"做什么"，而非"怎么做"
- 每个测试一个逻辑断言

## 接缝（Seams）— 测试的位置

**接缝**是你进行测试的公共边界：观察行为而不深入内部的接口。测试存在于接缝处，而非针对内部实现。

**只在预先约定的接缝处测试。** 编写任何测试之前，先确认被测接缝。你无法测试所有东西——提前约定接缝确保测试精力落在关键路径和复杂逻辑上。

## 反模式

避免这些常见错误：

- **耦合实现** — mock 内部协作者、测试私有方法、或通过旁路验证。征兆：重构后测试失败但行为未变。

- **同义反复** — 断言以与代码相同的方式重新计算期望值，因此它通过构造永远通过，永远无法与代码产生分歧。期望值必须来自独立的事实源。

- **横向切片** — 先写所有测试，再写所有实现。批量测试验证的是想象中的行为。应该用**垂直切片**：一个测试 → 一个实现 → 重复。

## 循环规则

- **先红后绿。** 先写失败测试，然后只写刚好能让它通过的代码。
- **一次一个切片。** 一个接缝、一个测试、一个最小实现。
- **重构不属于循环。** 它属于审查阶段，而非红→绿的实现循环。

## 何时 Mock

只在**系统边界** mock：
- 外部 API（支付、邮件等）
- 数据库（有时——优先用测试数据库）
- 时间/随机数
- 文件系统（有时）

不要 mock：
- 你自己的类/模块
- 内部协作者
- 你控制的任何东西

**为可 mock 性设计：** 使用依赖注入——将外部依赖传入而非在内部创建。优先使用 SDK 风格接口而非通用获取器。
